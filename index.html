01How to trigger events

Publish once, every matching task runs.

A fifth way to start a run, next to direct triggers, schedules, webhooks and agent sessions. Type-safe from publisher to subscriber.

1

Define

src/trigger/events.ts

The contract: a name and a schema.


export const orderCreated = events.define({
  name: "order.created",
  schema: z.object({
    orderId: z.string(),
    total: z.number(),
    country: z.string(),
  }),
});

Registered on trigger dev and deploy, so the server knows every event name.

2

Subscribe

src/trigger/events.ts

A task listens with on, narrows with filter.


export const sendReceipt = events.task({
  id: "send-receipt",
  on: orderCreated,
  run: async ({ payload }) => { … },
});

export const notifySalesIt = events.task({
  id: "notify-sales-it",
  on: orderCreated,
  filter: { country: "IT" },
  run: async ({ payload }) => { … },
});

Each run gets { id, name, timestamp, payload }, payload typed by the schema.

3

Publish

backend or task

One HTTP call. It returns an event id, not run ids.


import { events } from "@trigger.dev/sdk";
import type { orderCreated } from "./trigger/events";

// From your backend
await events.publish<typeof orderCreated>(
  "order.created",
  { orderId: "o_301", total: 49.5, country: "IT" },
  { idempotencyKey: "o_301" }
);
// → { id: "evt_…", status: "PENDING", … }

// From a task: import the definition, then
await orderCreated.publish(order);

Or POST /api/v1/events with the secret key.

02Event lifecycle and the deploy gap

Six statuses, one owner per transition.

Status is a column on Event, written by the publish route, the fan-out job, the registration sync or the sweeper.

If 2 tasks match
✓✓both startDISPATCHED
✓✕one startsDISPATCHED+ error
✕✕neither startsFAILED

Normal path

Each matching task gets its own run. A task that can't start for a temporary reason, like a full queue, is tried up to 5 times. Tasks that already started are not started again.

Deploy gap

Published before the worker that defines the name? Parked as PENDING_DEFINITION instead of a 404, released when a worker defines it, and marked UNDEFINED after 15 min so a typo stays visible.

04Fair delivery between environments

Every environment gets its turn.

A burst in one environment used to make the others wait. Now environments take turns, and none can fill every worker.

Delivery order during a burst

A and B are two environments, say two customers' production. A publishes 750 events at once, each with 20 subscribers. Then B publishes one.
Beforeone line, oldest first
B waits for all 750 of A's15,000 runs start before B's
Nowa line per environment
B goes almost at oncetested: within the next 10 deliveries
1

Turns: who goes next

ProblemOne line for everyone: B's one event waits behind A's 750.

FixA line per environment. Each round takes up to 5 events from every line that has some.

waitingA× 750B× 1C× 7
round 1
round 2
round 3

→ B goes in round 1, not after A's 750.

The rounds are Deficit Round Robin, from FairQueue in @trigger.dev/redis-worker.

2

Cap: keep workers free

ProblemTurns are not enough. A worker stays busy until its delivery has started all 20 runs, so A's deliveries could fill all 20 workers.

FixOne environment can use at most 15 of the 20 workers, so 5 stay free for the others.

→ B gets a free worker right away.

05Infinite loops

Every loop stops at hop 10.

A task that publishes the event it listens to would start runs forever. So every event counts how many events led to it.

!

The loop

example

A task that publishes the event it listens to.


export const auditOrder = events.task({
  id: "audit-order",
  on: orderUpdated,
  run: async ({ payload }) => {
    await saveAuditLog(payload);
    // publishes the event it listens to
    await orderUpdated.publish(payload);
  },
});

Each run publishes a new order.updated, which starts another run. Without a limit, it never stops.

✓

The fix: count the forwards

Like an email: each forward adds one "Fwd:". The system counts them and stops at 10.

hop 0Order updated✓ audit-order runs
hop 1Fwd: Order updated✓ audit-order runs
hop 2Fwd: Fwd: Order updated✓ audit-order runs
⋮
hop 10Fwd: Fwd: Fwd: Fwd: Fwd: Fwd: Fwd: Fwd: Fwd: Fwd: Order updated✕ refused → FAILED

Email = event · forward = the task publishes again · number of "Fwd:" = hop

Saved on the event as a hop column. The runs it starts keep a copy, so their next event gets hop + 1.

One order update, hop by hop

audit-order publishes order.updated every time it runs
hop 0 · a new event from your backend 10 runs, then it stops hop 10 · refused → FAILED

Tested: a ping-pong between two tasks stops at hop 10 with exactly 10 runs. Limit: it caps how deep a chain goes, not how wide.

06Rate limit per event name

A loop through your backend hits a limit.

The hop limit can't see a loop through your backend. This rate limit doesn't stop it either: it limits the damage to one event name.

!

The loop, in code

src/trigger/crm.ts · your backend

export const syncCrm = events.task({
  id: "sync-crm",
  on: orderUpdated,
  run: async ({ payload }) => {
    await callBackend("/orders/" + payload.orderId + "/sync"); // your backend
  },
});

// ...whose /sync route publishes order.updated again
await events.publish<typeof orderUpdated>("order.updated", { orderId });

Why the hop limit misses it

A task's event knows the run that sent it, so each one is a hop more. Your backend's event has no run, so it starts over at hop 0.

Task publishes
012345678910
stops at hop 10
Backend publishes
00000000000⋯
never stops

Not strictly needed: the API rate limit and the fair queue already protect the platform. This one holds back only the looping name, not every call made with the API key.

A small loop runs on: one order looping stays under every limit.

A limit per event name

1,000 a minute by default

Each environment may publish 1,000 events of one name per minute. Above that, new ones are saved but not delivered.

1,000 deliveredrate limited
0limit: 1,000 in a minute1,400

→ The publish answers THROTTLED, no run starts, and the event shows as Rate limited

EVENTS_NAME_RATE_LIMIT_PER_MINUTE sets the number, and 0 turns it off.

Safe for normal traffic

  • You hear about it once: one alert a minute per event name, sent to Sentry.
  • It lifts on its own: rate-limited events don't count, so the name is delivered again once the loop slows.
  • It never blocks a publish: if the limit check fails, the event goes through.
  • You can send it again: a rate-limited event frees its idempotency key.

✓ Tested: the 3 new tests in publishEvent.test.ts pass. With a limit of 5, 8 events give 5 delivered, 3 rate limited and one alert; other names and environments are not limited.

07Subscribers per event

100 subscribers per event, for now.

One job delivers an event to all its subscribers, one after another, and must finish within a 60-second lease.

One delivery job, one 60-second lease

Subscribers are triggered one by one; about 2,000 fit. Past that, the queue thinks the job died and starts it again.
100 subscribers 2,500 subscribers ↳ second copy
0 s30 s60 s90 s
lease ends → another worker starts the same job
≈ 3 s · done, wide margin ≈ 75 s · runs past the lease starts again from subscriber #1
What the second copy does

Calls trigger 2,500 more timesMost get back the existing run: same idempotency key

2×

Re-runs tasks that already failedA failed run frees its key, so a second run starts

Writes the Event row againOverwrites the saved result about a minute later

First: cap subscribers per event name

S · up to ½ day

When a worker registers (trigger dev or deploy), count the subscribers of each event name. Above 100, fail before anything is written.


const MAX_SUBSCRIBERS_PER_EVENT = 100;
if (count > MAX_SUBSCRIBERS_PER_EVENT) {
  throw new ServiceValidationError(message);
}
✕ deploy failsorder.created has 2,500 subscribers; the limit is 100

Current subscriptions keep working. 100 subscribers take about 3 s, far inside the lease.

Later: chunk large deliveries

M · 1 to 2 days

One parent job splits the subscribers into jobs of 50. Each job gets its own 60-second lease and needs only a second or two.

event.fanOut2,500 subscribers → 50 chunks
#150 tasks
#250 tasks
#350 tasks
#450 tasks
#550 tasks
#650 tasks
⋯
#5050 tasks

each chunk job: 50 triggers, ≈ 1–2 s of its 60 s lease

A small table tracks the chunks; the last one to finish writes the event's status. Then the cap is lifted.

08Event payload size

Payloads up to 256 KB, for now.

Every run gets its own copy of the payload. Past 512 KB, each copy is uploaded to the object store.

One event, one upload per run

Each run gets the payload in its own envelope; over 512 KB, the trigger service uploads it under the run's id.

Now: cap event payloads at 256 KB

A publish over 256 KB is refused with a 413, before anything is stored or queued.


const maxPayloadBytes = env.EVENTS_PAYLOAD_MAXIMUM_SIZE ??
  Math.floor(env.TASK_PAYLOAD_OFFLOAD_THRESHOLD / 2); // 256 KB
if (payloadSize > maxPayloadBytes) {
  throw new ServiceValidationError(message, 413);
}
✕ 413Event payload is too large (300.1 KB). Maximum allowed size is 256.0 KB.Reduce the payload size, or store large data elsewhere and publish its id or URL.

Why half of 512 KB: each run's envelope is a bit bigger than the payload (superjson adds 8 bytes per date). Under 256 KB it stays under 512 KB, so nothing is uploaded.

✓ Tested: 1 byte over is refused, nothing saved; exactly 256 KB reaches 3 runs inline.

Later: share large payloads across runs

M · 1 to 2 days

Build the envelope once per event and upload it once. Every run points to that one file, as batch items already do.

events/evt_…/envelope.json2 MB · uploaded once
run 1no upload
run 2no upload
run 3no upload
run 4no upload
run 5no upload
run 6no upload
⋯
run 20no upload

2 uploads per event, whatever the number of subscribers

today · 21 uploads · 42 MB→later · 2 uploads · 4 MB

The runs read one file instead of 20 copies. Then the cap can be raised, up to the 3 MB task payload limit.

11Ideas and extensions

Ideas to extend events.

Not planned yet. The code lines sketch how each one could look.

Build agents on a canvas

Drop events and tasks on a canvas and connect them. The canvas writes the code: an agent that wakes up on events and calls tasks as its tools.

  • Starts from what is deployed: the environment's events and tasks.
  • Saved as code, so it lives in git and deploys like any task.

Wait for an event in a run

A run pauses until a matching event is published, like a waitpoint token.

await wait.forEvent(orderPaid, { orderId })

Webhooks become events

A URL per event name, so Stripe or GitHub can publish without code, with the signature checked.

POST /hooks/stripe → payment.succeeded

Publish now, deliver later

A delay or a date on publish, like a delayed task.

orderCreated.publish(order, { delay: "1h" })

Join events

Start a task once both events have arrived for the same order.

on: [orderPaid, orderShipped], by: "orderId"

Batch subscribers

One run per 100 events, or per minute, instead of one run per event.

batch: { size: 100, window: "1m" }

Send events outside tasks

Deliver them to an HTTP endpoint or Slack, or stream them to your frontend.

events.webhook({ on: orderCreated, url })
